# Test execution record specification

## Identity and selection

- **Specification ID:** `TEST-EXECUTION-RECORD@core`.
- **Purpose:** Record what happened during one bounded, actually initiated test run, including the tested configuration, attempted cases, observations, deviations, and results.
- **Intended readers:** Test operators, test leads, defect investigators, reviewers, and people who use actual results in a later verification or completion decision.
- **Decision or action supported:** Readers can reconstruct the run, judge each reported outcome against its expected result, identify anomalies and missing evidence, and decide what needs investigation or retest.
- **Use when:** Test activity has actually begun and its observations, abort, or case results need an evidence record. One run may include several case attempts under the same run identity and scope.
- **Scope boundaries:** One initiated, bounded test run. Record selected unattempted cases and actual attempts distinctly, with each outcome tied to the work and observations that occurred.

## Authoring inputs and unresolved facts

Obtain the actual run identifier and scope; applicable test authorization or standing execution authority; tested item and actual build or configuration; the case, procedure, script, or other inspectable test definition and its edition; expected results and pass criteria; actual environment, data, instrumentation, operator or tool identity; event times; observations and raw evidence; deviations, anomalies, and any retest linkage. Identify the exact test definition and actual configuration in this record, with locators for separately retained definitions and configuration details when they exist.

If a timestamp, configuration element, observation, or evidence item was not captured, state the gap, its effect on the result, and the actual recovery or investigation action. Do not reconstruct missing observations, substitute a planned configuration for the one used, or infer a pass without an observation supporting the established criterion. If authorization was required but cannot be substantiated, state the execution-control issue without erasing or upgrading the technical outcome. Classify each `not-run` entry or attempt with the outcome rules below. The run must have been initiated. Cases never selected for this run stay outside it. Preserve an aborted run and a failed attempt; a later retest gets a distinct attempt identity and links back to the original. When no separate case or procedure exists, state the exact definition used here and do not invent its identifier.

## Finished-document contract

- **Title:** Identify the test item or effort and the actual run, and name the document as a test execution record.
- **Frontmatter:** None. Begin with the GFM title. Run identity, configuration, and results belong in the body.
- **Client or receiving party:** Conditional body element in the identity or scope section. Include it only when a named external party commissions or receives the work; then state that party's established name and relationship, such as client or receiving organization. When no external party exists, state that the document has no external client. Do not invent a party. Do not put the party in the specification ID, filename, or type name.
- **Order:** Establish the real run and execution context before case outcomes; present reconciliation and limitations after the observations. Heading wording may vary.

| Section role | Status and inclusion condition | Content obligation |
|---|---|---|
| Run identity, scope, and authority | Required | Identify one bounded run, its actual start and end or abort state, target and limits, operator or automation identity, and the actual project authorization or standing permission, its decision maker or issuer, and its execution limits where execution control required it. Record this authorization independently of the technical outcomes. |
| Test basis and actual configuration | Required | Identify the actual item/build, environment, data, tools or instrumentation, and relevant versions or baselines used. Do not substitute the plan's intended configuration for the configuration used. If an actual identity is unknown, say so and limit any comparison that depends on it. Identify the applicable test definitions, expected results, and criteria by real edition and locator, or state them in this record when no separate controlled definition exists. Record material drift from the planned configuration. |
| Attempted cases and observations | Required | Give one `not-run` entry for each case selected for this run for which neither a test stimulus nor a result assertion was performed, and one entry for each actual attempt, including a retest. If the run ended before any case was selected, say so and do not invent a case. Record actual times, actions or steps performed, observations or measurements with units where relevant, evidence locators, deviations, and comparison with expected results for each attempt. Link anomalies and later retests to the affected attempt. |
| Reconciliation and limitations | Required | Reconcile selected cases, `not-run` entries, distinct attempts, retests, pass/fail/inconclusive outcomes, and any aborts against the entries. Do not replace several attempt outcomes with one case outcome. Explain missing evidence, incomplete steps, environmental changes, and other limits on the conclusion. State actual review or disposition only if it occurred; identify open investigation or retest actions without presenting them as complete. |

## Content definitions and forms

| Element | Meaning and cardinality | Constraint |
|---|---|---|
| Run identity | One unique, stable identity for the bounded run. | Bind the record to the actual tested item, scope, and time window. Do not combine separate campaign runs under one identity merely to summarize progress. |
| Execution authority | One applicable authority basis when the project controls execution. | Identify the actual project approval, change authorization, standing permission, or execution-control decision and its limits. When no distinct authorization is required, state that project execution-control decision and the role that established it; if this basis is unknown, state the gap. |
| Test definition | Zero when the run ended before any test definition was selected. Otherwise each selected case or attempt identifies the definition that applies to it. | That definition is a real case, procedure, or script, or text stated in this record. Give an ID, title, edition, and locator only when that controlled definition exists. When none exists, state the objective, stimulus or steps, and expected result here and do not invent an identifier. Record performed actions and observations separately from the definition. |
| Actual configuration | One observed run configuration, with per-attempt differences when they matter. | Identify software or hardware version, environment, data set, setup, and instrumentation sufficient to interpret or reproduce the result. Unknown is not the planned value. For an attempt, a comparison that depends on an unknown configuration is `inconclusive` or explicitly limited. That uncertainty does not turn a `not-run` entry into an attempt. |
| Case or attempt entry | Zero after an assessed statement that no case was selected. Otherwise one `not-run` entry for each unattempted selected case, and one entry for each attempt. | Give every attempt a distinct stable ID. Identify its test definition, performed stimulus or assertions, start, end, or abort time, actual actor or tool, observed result, evidence, and outcome. `not-run` means neither a test stimulus nor a result assertion was performed, including a stop for a failed prerequisite, another blocker, or an abort before either action. Give that reason. A campaign case that was not selected for this run is omitted, not marked `not-run`. |
| Time | Actual event time for the run and each attempted case, when separately meaningful. | Use a date-time with a timezone, and preserve the observed precision. If a time was not captured, mark it unknown and explain the resulting limitation; do not estimate it as fact. |
| Observation and evidence | Zero for a `not-run` entry. For an attempt, one or more observations when they were captured. | Preserve values, units, logs, images, or raw-data references with accessible locators and integrity context when needed. A `pass` or `fail` needs the observation that supports that outcome. If that observation was not captured, say so and classify the attempt `inconclusive`. Redact secrets without destroying the ability to assess the outcome. |
| Outcome | One status for each `not-run` entry or attempt entry. Use none when no case was selected. | Do not roll several attempts of one case into a single status. Use `not-run` only for a case selected for this run for which neither a test stimulus nor a result assertion was performed. Use `inconclusive` when a stimulus or result assertion was attempted but the comparison is not supportable, including a missing oracle, a missing observation, an invalidating condition, or an abort after the attempted stimulus or assertion without a demonstrated miss. Use `fail` only when an established criterion was missed and the observation shows that miss. Use `pass` only when an established expected result and a supporting observation agree. A technical outcome does not establish that execution was authorized. |
| Deviation, anomaly, and retest link | Zero or more real deviations, anomaly references, or links to a distinct retest. | A `fail`, `inconclusive`, or abort needs a stated disposition or unresolved investigation path. A `not-run` entry needs its reason. Never overwrite a failed attempt with a later pass; link the attempts and keep both outcomes. |
| Counts | One reconciliation for the bounded run. | Count selected case identities, `not-run` entries, actual attempts, retests, and each attempt outcome separately. `not-run` entries are not attempts. A later pass does not remove an earlier `fail` or `inconclusive`. |

Use a compact run-context block and a table or ordered entries with meaningful case ID, test definition, actual observation, evidence, and outcome fields. Use a per-step table when step sequence or deviation matters; retain raw measurements by reference instead of copying large logs into the record. A diagram or screenshot MAY serve as evidence only when its source and the observation it supports are identified. Do not add blank case rows or a generic completion checklist.

## Quality criteria

- The run identity, observed configuration, test definition, actor or tool, and times identify the event being reported. Planned configuration and method text are not substituted for them.
- Every `pass` or `fail` cites the expected criterion and the observation that supports it. A missing basis, a missing observation, or an abort after the stimulus without a demonstrated miss is `inconclusive`. `not-run` is unattempted selected work, and unselected planned cases are not listed as `not-run`.
- Counts reconcile selected cases, `not-run` entries, and distinct attempts, including aborts and retests. Failure history remains visible.
- Anomalies, deviations, and configuration drift are traceable to the affected result and have an actual disposition or open action.
- The record reports testing that occurred. It identifies actual execution authorization or an unresolved authorization gap, and any review or disposition with its actual decision maker and scope. Technical outcomes remain bound to performed attempts and their supporting observations.
