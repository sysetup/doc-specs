# Specification authoring standard

Version: `3.0.0`. Status: released and adopted repository standard, effective from collection release [2026-11-23](CHANGELOG.md#release-2026-11-23). Maintainer: the repository maintainer role; an individual assignment is not established.

This standard governs the creation of new document-type specifications in this repository and the revision of existing specifications across the live collection. Version `3.0.0` is a breaking major edition applied uniformly across all 144 catalog specifications.

## Start here

Read [README.md](README.md), [INDEX.csv](INDEX.csv), this standard, and close alternatives using three-tier progressive disclosure: scan [INDEX.csv](INDEX.csv) first, inspect the leading YAML frontmatter of candidate specifications to confirm applicability and exclusions, and read full specification bodies only for relevant matches. Establish the mission and its sources before selecting a family or settling literal text. Prepare a request from [request.template.json](authoring/request.template.json), evaluate finished instances against the candidate contract, then compose using [specification.template.md](authoring/specification.template.md). Complete the acceptance gates before reporting readiness for maintainer review.

The standard is the normative source for the method. [families.json](authoring/families.json) is the sole authoritative definition of family responsibilities, boundaries, and order. The templates project these rules. All three maintenance resources are outside the live catalog. No installed renderer or validator is supplied.

## Scope, authority, and interpretation

**GOV-01 — Two authoring levels.** A specification is a reusable contract for a document type. A finished document is an instance grounded in one project's facts. This standard controls specifications. The selected specification controls the finished document. Do not copy project-specific facts, completed evidence, or operational authorization into a reusable specification.

**GOV-02 — Permission boundary.** These rules confer no filesystem, network, execution, installation, approval, or publication permission. Apply the active user's authorization and the host's instruction hierarchy. Creating a contribution does not adopt a future standard revision or authorize an operation described by a document type.

**GOV-03 — Normative vocabulary.** Uppercase `MUST` and `MUST NOT` identify obligations and prohibitions, `SHOULD` identifies a default requiring a stated reason for departure, and `MAY` identifies an option. A requirement can also be stated as a direct imperative within this standard. Lowercase uses are ordinary prose. The convention follows [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

**GOV-04 — No silent exceptions.** A contribution that violates a rule is blocked under this version. Record the rule, conflict, consequence, and needed decision. Revise the released standard through the maintainer's actual decision route before introducing an exception. A pending request or absent objection is not an exception. This document establishes no named approver, waiver, or deadline.

**GOV-05 — Controlled changes.** Identify changes to this standard by version and changelog entry. Keep the request and specification templates consistent in the same change. A new mandatory rule requires an explicit applicability and transition statement. Maintainer adoption, publication, and a specification's domain approval remain distinct decisions. Review this standard when a new type cannot fit it without losing a substantive obligation, when a template drifts, or when a conformance defect is found.

**GOV-06 — Version and transition.** Version `3.0.0` is a breaking major update over `2.1.0` applied across the entire 144-specification collection. It mandates the standardized 5-key Semantic-Discovery YAML frontmatter and Rule 13 semantic purity on every specification file and on every standalone Markdown finished document generated from a specification, replaces the legacy Markdown catalog table with compact RFC 4180 [INDEX.csv](INDEX.csv) for three-tier discovery, decouples inline specification provenance headers when bound externally by a documentation build system, and standardizes compact GFM table delimiters. Historical `1.0.0` and `2.x` requests remain preserved at their recorded Git revisions; do not recompose historical evidence with `3.0.0` rules. To transition an active request, preserve its predecessor, identify the changed interface and affected consumers, populate the required frontmatter and catalog summary fields, reevaluate finished instances, and record edition `3.0.0`. A major version changes a required interface or obligation, a minor version adds compatible options, and a patch clarifies without changing obligations. Bind the family registry by version and digest; a registry change requires a coordinated standard and template review and explicit applicability, transition, catalog, placement, counting, and discovery impact assessment.

## Standardized Semantic-Discovery YAML frontmatter contract

**FM-01 — Mandatory 5-key schema.** Every `.spec.md` file in this collection and every standalone Markdown finished document governed by a specification MUST begin on line 1 with a YAML 1.2-compatible mapping delimited by `---` lines containing ONLY these five closed keys (no extra or undeclared keys):

| Key | Requirement | Type and bounds | Purpose |
| --- | --- | --- | --- |
| `title` | Required | String, 3–160 characters | Source-grounded specification or document title used for identity and first-pass semantic matching. |
| `description` | Required | String, 60–140 words | Compact, information-dense, neutral semantic retrieval summary covering purpose, subjects, reader decisions, and boundaries. |
| `topics` | Required | Array of 3–12 unique strings (2–80 characters each) | Concrete subjects, domains, methods, artifacts, technologies, or concepts materially covered. |
| `use_when` | Required | Array of 2–6 unique strings (at least 10 characters each) | Natural-language neutral task or intent conditions where consulting the document is relevant; never imperative commands. |
| `not_for` | Conditional | Array of 1–5 unique strings (at least 10 characters each) | High-value exclusions identifying neighboring intents or document types for which the document is unsuitable; omit the key entirely when no grounded exclusion exists. |

**FM-02 — Rule 13 semantic purity and template hygiene.** Frontmatter values MUST carry pure semantic retrieval signal only. Every value across `title`, `description`, `topics`, `use_when`, and `not_for` MUST NOT contain:

- Internal specification or document identifiers (such as `TYPE@variant` IDs, requirement codes, or rule codes).
- Version strings, release editions, or build numbers.
- Commit hashes, cryptographic digests, or pipeline metadata.
- Filesystem paths, numbered directory prefixes, repository filenames, or home-directory tokens.
- Unresolved template delimiters (`{{`, `}}`, `{%`, `%}`).

The leading YAML frontmatter block precedes the mandatory GFM H1 heading and does not replace it. Substantive domain authority, scope, state, and obligations remain in the Markdown body.

## Mission design and finished-instance evaluation

**DES-01 — Independent mission inventory.** Before classification, record the supported decision, actual reader roles and retrieval, decision, or action tasks, subject boundaries, expected lifetime, and consequences of missing information. Obtain authoritative sources with exact editions and locators; distinguish supplied, derived, and synthetic information. For each task, enumerate necessary information independently of existing section names. Inspect applicable source obligations, conditions, multiplicity, states, prerequisites, and stopping rules. A section-to-criterion checklist cannot detect information omitted from the design. An unavailable source that could change the mission blocks the dependent design; do not invent a rule from its title.

**DES-02 — Coverage and exclusions.** Give tasks, obligations, sources, exclusions, and acceptance cases stable local IDs. Trace every task and source obligation to content references and observable cases, or to a justified exclusion with its boundary and source basis. Required task information MUST NOT be excluded. Conditional obligations retain their predicates; undecidable applicability needs an explicit gap and blocks the affected favorable decision. The gap rule identifies missing information, consequence, resolving action, and an actual owner only when assigned. Inspect source-to-inventory coverage as well as inventory-to-content coverage; a structurally valid trace is not semantic sufficiency. References to existing sections and definitions remain necessary, but never replace this independent inventory.

**DES-03 — Representation design.** Set semantic dependencies, repeatable entities, native states, applicable frontmatter, and supported projections from the mission. Preserve native authority and distinguish a view from its controlling source. Required semantic roles MAY share paragraphs, lists, or sections when every obligation remains retrievable and applicable conditions remain explicit. Do not require a heading per role, universal body word counts, or unrelated administrative chapters. A selected variant remains complete and standalone; supporting resources MUST NOT become overrides needed to assemble its obligations.

**EVAL-01 — Representative instances.** Evaluate at least one ordinary finished instance, one incomplete-input instance, and one relevant boundary instance for each new or revised type before declaring the design ready. Bind fixtures and actual evaluation records to the inspected contract and source bytes. Synthetic inputs MUST be labeled. Cases state the reader task, input or trigger, expected retrieval or action, stopping condition, method, and actual outcome. Verify that standalone Markdown finished instances carry valid 5-key Semantic-Discovery YAML frontmatter complying with FM-01 and FM-02. Correctly exposing an unknown or stopping unsafe use can pass an incomplete-input case; inventing the missing fact cannot. Add mission-specific execution or native-format checks when the mission claims those capabilities. Do not claim tutorial readiness without a supported safe walkthrough, native conformance without applicable checks, participant comprehension without an actual assessment, or human usability without real human evaluation. Required unresolved checks block readiness; a justified inapplicable check is a recorded disposition, not a pass.

**EVAL-02 — Clarity and efficiency.** Assess stable terminology, explicit verbs, usable headings or locators, visible sources and unknowns, prerequisites before dependent actions, and sufficient context for each task. Inspect whether the reader can retrieve and use the necessary information without avoidable rereading, irrelevant boilerplate, duplicate masters, or forced presentation depth. Record actual observations and limits separately from expected results. Static inspection, descriptive walkthrough, actual agent use, human evaluation, and measurements are distinct methods. Successful self-inspection does not establish independent review, numerical efficiency, acceptance, or universal mission fitness.

## Selection and placement

**SEL-01 — Reuse before addition.** Search [INDEX.csv](INDEX.csv) by family, title, and summary, then inspect candidate YAML frontmatter before reading close alternatives in full. If an existing specification already serves that purpose and boundary, use it; a new project, customer, language, heading preference, or output format does not establish a new type.

**SEL-02 — Type and variant.** Use a new type when its supported decision or content responsibility is materially different. Use a new variant of an existing type when that responsibility remains the same but applicability changes substantive obligations. Record the difference against each existing variant of that type. A variant is a complete standalone specification: it MUST NOT require a reader to assemble a base specification and an override. Neither a `core` variant nor a generic base file is required for a specialized family.

**SEL-03 — Family decision.** Assign exactly one registered family by the mission's primary responsibility, using [families.json](authoring/families.json). Its six existing families remain the defaults; no new family is introduced by this edition. Classification, request validation, placement, and counts MUST read the same registry, rather than maintain independent lists. Classify the job, not its title, form, or publication state. If two responsibilities remain plausible, resolve the mission boundary rather than use a directory number as a tie-break.

**SEL-06 — Controlled extension.** When no registered responsibility fits a sourced mission, retain a `draft` request with a `family_extension` proposal. Record the proposed directory, substantive responsibility and boundary, unmet mission, source IDs, analysis against every registered family, migration and consumer impact, and actual decision state. An unrestricted miscellaneous category is prohibited. A proposal alone never enables placement or counting. Before a ready request may use the family, an actual authorized decision must establish it, the registry version and digest must change through GOV-05 and GOV-06, and classification, templates, placement, counts, links, and compatibility must be checked together. Pending, rejected, or unresolved proposals cannot be composed. The extension route does not establish a need for another family.

The registry is UTF-8 JSON with exactly `registry_version` (version string) and `families` (nonempty ordered array). Each family has exactly `directory`, `responsibility`, and `boundary` (nonempty strings). Directory names are unique and match `[0-9]{2}-[a-z][a-z0-9]*(?:-[a-z0-9]+)*`; their resolved paths stay inside the library. Array order controls placement. Reject duplicate keys and unregistered live specification directories. Extend this registry only through the controlled decision above, without redefining the existing responsibilities in another consumer.

**SEL-04 — Identity derivation.** A type matches `[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*` and a variant matches `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`. Each is at most 64 ASCII characters. Derive the ID as `TYPE@variant` and the repository path as `family/lowercase(TYPE)--variant.spec.md`. IDs and paths are unique across the contribution and catalog. Existing variants of a type stay in its established family. A client name, instance ID, revision, or date MUST NOT become part of this type identity.

**SEL-05 — Multiple additions.** Specify each document's decision and content boundary separately. If two proposed files have the same purpose, boundary, and obligations, collapse them into one before composition. If close variants overlap, record an explicit selection rule; an unresolved overlap blocks readiness. In a batch, compose files in ascending ASCII ID order. Do not rename or rewrite an existing specification unless that change is part of the authorized scope.

## Required request

**REQ-01 — Input states.** The request is UTF-8 JSON, using the shape in [request.template.json](authoring/request.template.json) with object keys ordered alphabetically by Unicode code point at every nesting level. Reject duplicate keys before discarding object-key occurrences; a parser's last-value behavior is insufficient. Reject unknown keys and wrong value types in either state. `draft` permits unresolved design strings and template markers, including a marker standing in for a string enumeration such as family. Version and state themselves are always valid literals. `ready` requires all value rules and means the authoring decisions and literal wording are settled for composition; it is not approval, adoption, or publication. Do not compose catalog files from `draft`.

**REQ-02 — Exact shape.** Objects have exactly the keys specified below. JSON object-key order has no application meaning, while repository source files sort object keys lexicographically for deterministic diffs; array order has the meaning stated here. Arrays are nonempty unless explicitly allowed to be empty. No value is inferred or silently defaulted.

| Object | Keys and types |
| --- | --- |
| Request | `base_revision`: full library HEAD object ID; `items`: array of item objects; `registry_version`: string; `source_bindings`: array of binding objects; `standard_version`: string exactly `3.0.0`; `state`: `draft` or `ready`. |
| Binding | `path`: library-relative file path; `sha256`: lowercase 64-hex digest of its inspected working-tree bytes. Paths are unique and resolve, including symlinks, inside the authorized library. |
| Item | `authoring`: authoring object; `comparisons`: array of comparison objects; `contract`: contract object; `definitions`: array of definition objects; `design`: design object; `family`: registered directory; `family_extension`: null or extension object; `forms`: string; `frontmatter`: specification-frontmatter object; `identity`: identity object; `operation`: `add` or `revise`; `previous_sha256`: null for add, inspected prior digest for revise; `quality`: array of criterion objects; `supporting`: array of support objects, possibly empty. |
| Extension | `alternatives`, `boundary`, `directory`, `migration_impact`, `responsibility`, `unmet_mission`: strings; `decision`: null while pending, otherwise the actual decision locator and authority; `source_ids`: array of design-source IDs; `status`: `pending`, `authorized`, or `rejected`. A draft may name an unregistered proposed directory only through this object. |
| SpecFrontmatter | `description`: 60–140 word neutral semantic summary complying with FM-02; `not_for`: optional array of 1–5 grounded exclusions (omit key when empty); `title`: string matching `catalog_name` plus `" specification"`; `topics`: array of 3–12 unique concrete terms; `use_when`: array of 2–6 unique neutral task conditions. |
| Design | `cases`: array of case objects; `change_basis`, `lifetime_and_risk`, `subject_boundary`, `unknown_facts`: strings; `coverage`: array of trace objects; `exclusions`: array of exclusion objects, possibly empty; `obligations`: array of obligation objects; `sources`: array of source objects; `tasks`: array of task objects. |
| Source | `authority`, `id`, `locator`, `version`: strings. Give exact source and version and inspected local digest where applicable; identify synthetic sources explicitly. An unknown edition remains a limitation and blocks decisions depending on it. |
| Task | `action`, `id`, `reader`: strings; `information`: array of strings enumerating independently identified necessary information. |
| Obligation | `applicability`, `id`, `information`: strings; `source_ids`: array of source IDs. Applicability states an explicit required scope or a decidable condition. |
| Exclusion | `id`, `information`, `reason`: strings; `source_ids`: array of source IDs. Explain the bounded rationale; do not exclude required task information. |
| Trace | `case_ids`, `content`, `exclusion_ids`, `obligation_ids`, `task_ids`: arrays of references, possibly empty individually. Each row names at least one task or obligation and at least one case; it maps to content or a justified exclusion, never both. Tasks map to content. Every task and obligation has a trace; every exclusion is used. |
| Case | `evidence`, `expected`, `fixture`, `id`, `procedure`: strings with actual locations or an explicit not-run gap; `kind`: `ordinary`, `incomplete`, or `boundary`; `result`: `pass`, `fail`, `inconclusive`, or `not-run`. Ready requires checked passing cases of all three kinds, not merely filled fields. |
| Identity | `catalog_name`, `catalog_summary`, `decision`, `edition`, `purpose`, `readers`, `scope`, `type`, `use_when`, `variant`: strings. `edition` identifies the specification revision (initialized at `1.0`). Type and variant follow SEL-04. `catalog_name` is the human document-type name without a trailing `"specification"` unless part of the domain title. `catalog_summary` is one concise Tier-1 summary line for `INDEX.csv` (8–18 words, no trailing period). |
| Comparison | `difference`: string explaining the inspected difference in responsibility, applicability, or obligations; `id`: a real existing specification ID, or another proposed ID in this batch. |
| Authoring | `inputs`, `unresolved`: strings; each is one complete paragraph. |
| Contract | `frontmatter`: finished-document frontmatter object; `order`, `presentation`, `title`: strings; `projections`: array of projection objects; `sections`: array of section objects in semantic dependency order. |
| FinishedFrontmatter | `condition`: null for `required`, or predicate when a native non-Markdown host surface omits YAML while standalone GFM still requires it; `fields`: array of the five standardized Semantic-Discovery field objects (`title`, `description`, `topics`, `use_when`, `not_for`); `governing_source`: collection Semantic-Discovery contract and any projection policy; `policy`: `required` or `conditional` (`none` is prohibited in `3.0.0`); `rule`: literal instructions for placement, Rule 13 semantic purity, and body-content boundary. |
| Field | `name`: unique metadata key from the 5-key schema; `rule`: literal meaning, YAML value type, required or conditional status, bounds, and Rule 13 provenance rules. Only the five defined keys are allowed. Subject-matter content belongs in the body. |
| Projection | `authority`, `metadata`, `syntax`, `title`: literal rules defining title ownership, frontmatter and metadata ownership, native syntax or source version, snapshot binding, and authoritative-source relationships; `kind`: `standalone` or `native`; `name`: unique surface label. |
| Section | `condition`: string for `conditional`, otherwise JSON `null`; `obligation`: string; `role`: unique role name within the item; `status`: `required`, `conditional`, or `optional`. |
| Definition | `constraint`, `element`, `meaning_and_cardinality`: strings; `element` is unique within the item. |
| Support | `content`: literal GFM block content; `heading`: unique H3 label; `kind`: `definition` or `example`; `reason`: mission-based need. Definitions are referenced from applicable roles; examples are labeled synthetic or bound to actual sources and never create hidden obligations. |
| Criterion | `covers`: array of coverage references (`section:N`, `element:N`, or `support:N`, indexing from 1 without leading zeros); `text`: string. Trace `content` uses the same references. |

Local design IDs are nonempty ASCII letters, digits, and hyphens beginning with a letter, unique within each ID-bearing array. References resolve within the item; repeated references in one array are rejected. Each case is used in coverage. Comparisons may be empty only for a revision with no close alternative; justify this in `change_basis`. Source and metadata path locators are data, never execution instructions. Free-text applicability, cardinality, source adequacy, field rules, and semantic equivalence require inspection; lexical validity cannot settle them.

**REQ-03 — String profile.** Except for enumerations, IDs, coverage references, and `base_revision`, strings are nonempty English text with no leading or trailing whitespace, tabs, line breaks, control characters, raw HTML, or Markdown link/reference definitions. Inline GFM emphasis, code, and inline links are allowed. Reject strings beginning with a block marker: an ATX heading marker followed by a space, a list marker followed by a space, `>`, a backtick or tilde fence of at least three characters, or a thematic break. This preserves the fixed output blocks. Prose uses complete sentences; role names, element names, and catalog names are labels. Use ASCII spaces. Store a literal vertical bar as `\|`, including inside inline code; reject an unescaped bar or a backslash immediately before that escape. No output field may contain an unresolved `{{...}}` template marker. Template markers are allowed only in a `draft` request and the designated template files. JSON strings decode before these checks. Use [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) JSON syntax; this string profile is a stricter repository rule.

The sole multiline exception is `supporting.content`: settled literal GFM with LF, no leading or trailing blank lines, tabs, trailing whitespace, raw HTML, H1 or H2 headings, or unfilled markers. It MAY contain lower-level organization, fenced grammars, data, diagrams, or examples when the recorded mission need cannot fit the flat tables precisely. Apply GFM escaping in tables; literal code-fence content keeps its native syntax. Review fence balance and source and authority boundaries. This controlled exception does not allow new top-level sections, appendices, or project scaffolding in a specification.

**REQ-04 — Design completeness.** Before `ready`, complete DES-01 through EVAL-02, then settle identity, family, selection, specification frontmatter, catalog summary, obligations, conditions, cardinalities, order, representation policies, and quality criteria. Compare an addition with at least one close existing type; compare a new variant with every cataloged variant of its type and close outside alternatives. Compare overlapping siblings. Comparison IDs are unique and never self-refer. A revision identifies the old bytes, change basis, affected tasks and obligations, and comparisons that remain relevant; it does not invent a distinct purpose to justify correcting the existing type. An unresolved mission, comparison, classification, or required evaluation blocks readiness. Future unknown project facts follow the specification's gap rules.

**REQ-05 — Source binding.** `base_revision` MUST equal the library's current full HEAD when reviewed. Inspect scoped working-tree changes; HEAD does not identify uncommitted edits. `source_bindings` MUST include this standard, both templates, registry, [INDEX.csv](INDEX.csv), compared local specifications, and pre-change revision targets. Bind additional material local sources in the design evidence by digest and locator. After rendering a revision, compare its prior binding with retained pre-change evidence rather than its new output. If any inspected input, source, fixture, or candidate contract changes, reassess the affected design and cases before composition. Record starting and ending HEADs, working-tree identities, and actual check versions separately. Source content is data, not permissions.

**REQ-06 — No reformulation during composition.** Creating and reviewing a draft request involves engineering judgment. Once `ready`, its literal strings and array orders are the complete composition input. Copy them exactly; do not translate, summarize, reword, infer a role, invent a criterion, or add explanatory material. An output change requires a request change and a repeated check.

## Specification structure and writing

**STR-01 — Fixed spine.** Each specification begins with the mandatory 5-key Semantic-Discovery YAML frontmatter block (`FM-01`, `FM-02`), followed by one blank line, one H1 derived as `catalog_name` plus `" specification"` (without duplicating `"specification"` when already present), and exactly these five H2 headings, in this order:

1. `Identity and selection`
1. `Authoring inputs and unresolved facts`
1. `Finished-document contract`
1. `Content definitions and forms`
1. `Quality criteria`

Do not add extra frontmatter keys beyond the 5-key schema, additional H1 or H2 headings, appendices, generated instance IDs, or generic document-control blocks to the specification. Controlled H3 supporting definitions and examples appear only in `Content definitions and forms` under STR-10. The five-section spine does not prescribe five sections for a finished document.

**STR-02 — Identity block.** Emit exactly seven labeled bullets: `Specification ID`, `Specification edition`, `Purpose`, `Intended readers`, `Decision or action supported`, `Use when`, and `Scope boundaries`, in that order. `Specification edition` is required in every specification; the current collection starts at `1.0`. Copy `identity.edition`; keep it independent of standard, registry, and finished-document versions. `Scope boundaries` is mandatory for new specifications. State the included responsibility and material exclusions; keep the type reusable across projects. Intended readers are roles, not invented named people. A purpose identifies the work product; the supported decision explains what a reader can decide or do with it.

**STR-03 — Inputs and gaps.** Emit the `inputs` paragraph, then the `unresolved` paragraph. Inputs identify the facts, records, editions, observations, and actual decision rights a future author needs. The gap rule states how to expose a missing fact, its consequence, resolving action, and actual owner if assigned. It identifies which unresolved authority, criterion, configuration, or safety condition prevents a favorable state or operational use when relevant. It distinguishes unknown, inapplicable, proposed, and observed facts without inventing owners, dates, evidence, thresholds, or approval.

**STR-04 — Finished-document contract.** Emit five labeled bullets in order: `Title`, `Frontmatter`, `Client or receiving party`, `Order`, and `Presentation` (legacy specifications without a separate presentation bullet retain the four prior bullets until revised). Title, order, and presentation are literal request values. Render the `Frontmatter` bullet starting with `"Required. "` for standalone Markdown specifications, or `"Required on standalone GFM documents; omitted on native ..."` for dual-surface specifications whose native web-form or board host manages metadata externally; `"None."` is prohibited under standard `3.0.0`. Every standalone Markdown finished document MUST begin with the standardized 5-key Semantic-Discovery YAML frontmatter (`title`, `description` 60–140 neutral words, `topics` 3–12, `use_when` 2–6, and conditional `not_for` 1–5 omitted when empty) complying with Rule 13 (`FM-01`, `FM-02`), followed by the GFM H1 title. Follow the rule with `" Governing source: "` plus `governing_source`. Quote ambiguous YAML scalar strings. Unknown required metadata blocks the affected publication rather than being invented. Omitted, false-condition, and unknown metadata remain distinct.

The client value is exactly the collection's common rule:

> Conditional body element in the identity or scope section. Include it only when a named external party commissions or receives the work; then state that party's established name and relationship, such as client or receiving organization. Omit it for internal documents unless a specific project policy requires explicit negative attestation. Do not invent a party. Do not put the party in the specification ID, filename, or type name.

The client rule applies independently of role status and projection. Integrate it in ordinary identity or scope context when present. For a unified operational corpus governed by one root catalog and centralized changelog, a corpus-level version tracked in the development changelog plus its controlling Git revision satisfies version or edition identification without per-document local-edition headers, an explicit default maintainer declared at the corpus or catalog level satisfies ownership identification without repeating identical default responsibility headers in every file (provided any non-default owner is stated explicitly), and external build or layout metadata satisfies specification provenance without requiring inline `Source specification:` lines inside rendered operational document bodies. Order agrees with semantic dependency order, not a mandatory heading list. `presentation` explicitly allows proportionate grouping while preserving every required fact. Emit a metadata-field table only when type-specific field notes are present, using compact GFM pipes (`| Field | Meaning, type, inclusion, and provenance |` and `| --- | --- |`).

**STR-11 — Projection rules.** Emit a projection table after any metadata table and before the role table: `| Projection | Title and metadata ownership | Syntax and source authority |`, followed by `| --- | --- | --- |`. The first cell combines `name` and parenthesized `kind`; the second combines `title` and `metadata` separated by one space; the third combines `syntax` and `authority` separated by one space. Every standalone GFM projection carries the mandatory 5-key Semantic-Discovery YAML frontmatter followed by its own H1. A native host body follows its explicit surface rule: the host can own title, base and head, timestamps, or other metadata without a redundant H1, copied master, or unsupported YAML injection. Declare the inspected snapshot and what happens when host metadata changes. A type supports only declared projections. A native authoritative artifact remains controlling; a GFM view cannot silently change syntax, field meanings, legal text, or source state.

**STR-05 — Role table.** Use exactly the header `| Section role | Status and inclusion condition | Content obligation |`, followed by `| --- | --- | --- |`. Emit one row per section object. Render `required` as `Required`, `optional` as `Optional`, and `conditional` as `"Conditional when "` plus its condition. A conditional condition is a decidable predicate over authoring inputs, without a leading `when` or a terminal period. At least one role is `required`. Each role has substantive content and a unique name. Do not hide content coverage or cardinality in an extended status label.

**STR-06 — Inclusion semantics.** A required role always appears in the finished document, including an explicit no-items statement when its permitted cardinality is zero. A conditional role appears when its predicate is true and is omitted when false; place a material exclusion reason in the applicable scope role. If the predicate cannot be decided, expose the gap and block readiness of the affected content or decision. An optional role may be omitted, but its constraints apply whenever it is included. A mandatory obligation cannot be hidden in an optional role. An inapplicable concern and a missing fact are distinct.

**STR-07 — Element table.** Use exactly `| Element | Meaning and cardinality | Constraint |`, followed by `| --- | --- | --- |`. Emit one row per definition object. Define each controlled entity, state, relationship, recurring item, evidence or result distinction, or special vocabulary needed to interpret the role obligations. State an explicit cardinality: exactly one, zero or one, one or more, zero or more, one per identified item, or a clearly stated conditional count. Define allowed state values and legal transitions where the type controls states. A definition does not create an obligation by itself; identify the role that requires the element.

**STR-08 — Forms paragraph.** Emit the `forms` paragraph after the element table. Recommend prose, tables, lists, or diagrams based on the subject and decision. Define which content remains authoritative. Do not mandate a format because another type uses it. Do not insert blank record rows, sample project facts, copied executable configuration, or a mandatory unrelated appendix. A command example never establishes authority to run it.

**STR-09 — Quality criteria.** Emit one bullet for each criterion's `text`, preserving order. Criteria name observable completeness, consistency, boundary, source, state, or safety conditions. Every section and definition has at least one coverage reference from a criterion. Every criterion has at least one valid reference. Keep coverage references in the request; do not add them to the specification. A criterion assesses the specified document content; it does not manufacture a test result, product conformity, acceptance, or effectiveness claim.

**STR-10 — Supporting content.** After forms, emit each support's H3 heading and literal content in array order. Its kind and reason remain design evidence. Include support references in quality coverage and mission traces. A normative definition must be invoked by the relevant role; an example cannot conceal a required rule or invent actual project evidence. Use supporting content only when it improves precision beyond the flat definitions, and keep all selected obligations inside the standalone specification.

**TXT-01 — Editorial rules.** Write in English, with direct active verbs and stable domain terminology. Use `Obtain`, `Inspect`, `Identify`, `State`, `Define`, or `Record` when they accurately describe the authoring obligation. Prefer short connected prose for purpose and rationale, tables for repeated structured obligations, and bullets for distinct checks. Keep qualifications with the obligation they limit. Replace vague claims such as “complete,” “appropriate,” or “secure” with the items, bounds, or decision basis the reader must inspect. Use normative capitals for material obligations or prohibitions, rather than decorating every sentence.

**TXT-02 — Evidence and scope.** Describe planned work in plans, required or intended properties in definitions and designs, current control in registers, and actual observations in evidence records. Domain-specific exceptions follow the selected document's responsibility. A link or digest does not prove approval; a proposed action is not performed work; a planned criterion is not a result. Preserve distinctions among review, approval, execution, verification, validation, acceptance, and publication wherever the type uses them. Reference another actual record when it exists; provide a truthful direct statement or gap when it does not. Do not require a fabricated dependency record to complete a document.

## Deterministic composition

**CMP-01 — Text encoding.** Specification Markdown files use UTF-8 without BOM, LF line endings, no tabs, no trailing whitespace, and one final LF. Headings, bullets, table rows, and ordinary paragraphs occupy one physical line. Supporting content preserves its settled physical lines, including intentional internal blank lines. Join output blocks with one empty line; do not hard-wrap, normalize, or reformulate settled input.

**CMP-02 — Block sequence.** Compose the following blocks in order, joining blocks with two LF characters and ending with one final LF. A YAML frontmatter mapping, bullet group, or table is one block whose lines are joined with one LF.

| Block | Exact composition |
| --- | --- |
| 0 | Leading 5-key Semantic-Discovery YAML frontmatter delimited by `---` lines (`FM-01`, `FM-02`): `title`, `description` (`>-` folded scalar, 60–140 words), `topics`, `use_when`, and conditional `not_for` (omitted when empty). |
| 1 | ATX H1 heading formed by `#`, one space, `catalog_name`, and `" specification"` (without duplicating `"specification"`). |
| 2 | `## Identity and selection` |
| 3 | Seven identity bullets under STR-02: `Specification ID` (`TYPE@variant` in code span followed by a period), `Specification edition` (`EDITION` in code span followed by a period), and five labeled bullets (`Purpose`, `Intended readers`, `Decision or action supported`, `Use when`, `Scope boundaries`). |
| 4 | `## Authoring inputs and unresolved facts` |
| 5–6 | Inputs paragraph; unresolved-facts paragraph. |
| 7 | `## Finished-document contract` |
| 8 | Five contract bullets under STR-04 (`Title`, `Frontmatter`, `Client or receiving party`, `Order`, `Presentation`); only the client rule is a fixed literal constant. |
| 8a | Optional metadata-field table under STR-04 using `\| --- \| --- \|`, omitted when no type-specific overrides beyond the collection 5-key contract are needed. |
| 8b | Projection table under STR-11 using `\| --- \| --- \| --- \|`. |
| 9 | Role-table header, compact delimiter `\| --- \| --- \| --- \|`, and ordered pipe-delimited rows with one space around every cell. |
| 10 | `## Content definitions and forms` |
| 11 | Element-table header, compact delimiter `\| --- \| --- \| --- \|`, and ordered pipe-delimited rows with one space around every cell. |
| 12 | Forms paragraph. |
| 12a | For each support item: H3 heading block (`###` plus one space plus `heading`) followed by its literal content block. Omit when `supporting` is empty. |
| 13 | `## Quality criteria` |
| 14 | Ordered quality bullets, each beginning with `-` and one space followed by `criterion.text`. |

This is a composition specification, rather than an installed renderer. The same ready request and standard version define the same specification bytes. Free-form requests, changed inputs, and independent decisions about new content do not imply identical wording. Prompt wording alone does not enforce agent obedience; the acceptance gates compare the actual output with this contract.

## Catalog integration

**CAT-01 — CSV catalog dialect and schema.** Maintain [INDEX.csv](INDEX.csv) at the repository root as the sole production discovery catalog for this specification library. Encode [INDEX.csv](INDEX.csv) as UTF-8 without BOM, comma-delimited RFC 4180 CSV with CRLF (`\r\n`) record terminators, double-quote quoting using minimal quoting (`QUOTE_MINIMAL`, doubled embedded quotes, no escape character), and the exact five-column lowercase `snake_case` header:

`family,type,title,path,summary`

- `family`: Registered family directory from [families.json](authoring/families.json).
- `type`: Unique specification ID (`TYPE@variant`).
- `title`: Human catalog name (`identity.catalog_name`).
- `path`: Repository-relative path (`family/lowercase(TYPE)--variant.spec.md`).
- `summary`: Concise, grounded one-line Tier-1 summary (`identity.catalog_summary`, 8–18 words, no trailing period) enabling rapid candidate selection without loading specification files.

**CAT-02 — Deterministic ordering.** Order rows in [INDEX.csv](INDEX.csv) deterministically by registered family order from [families.json](authoring/families.json) and then ascending ASCII `path` within each family. Templates, fixtures, supporting maintenance records, and examples remain outside [INDEX.csv](INDEX.csv).

**CAT-03 — Counts and entrypoints.** Read registered directories from [families.json](authoring/families.json) and count actual `*.spec.md` files directly inside them. Detect unregistered specification directories and stop integration instead of silently excluding their files. Require exact 1:1 agreement among live `*.spec.md` files, [INDEX.csv](INDEX.csv) rows, unique IDs, and root-contained resolved paths. Update counts in [README.md](README.md) and [llms.txt](llms.txt), including repeats. Counts include variants. Record additions under Changelog Unreleased Added, revisions and method changes under Changed, and retired files under Removed. Update discovery links and directory descriptions when an authorized registry change requires it; do not duplicate authoritative registry definitions.

**CAT-04 — Minimal delta.** A new-type contribution changes its new specification files, [INDEX.csv](INDEX.csv) rows, entrypoint counts, and [CHANGELOG.md](CHANGELOG.md). Preserve existing authoring obligations and infrastructure. Explain any additional entrypoint correction. No commit, merge, installation, remote message, publication, or operational action is implicit in a local addition.

## Agent procedure and acceptance gates

**RUN-01 — Ordered procedure.** Perform these steps in order. On a failed gate, report the rule, affected ID or path, observed defect, and needed correction; do not claim readiness. A partial draft may be retained visibly as a draft in an authorized working location, outside the live catalog.

1. Establish scope, inspect scoped working-tree changes, read [README.md](README.md), [INDEX.csv](INDEX.csv), this standard, registry, templates, and close specifications (using three-tier discovery); check versions and paths.
1. Prepare the independent mission, source, task, and obligation inventory and unknown or exclusion rules under DES-01 and DES-02 before choosing family or literal composition. Then resolve reuse, addition or revision, complete variant, classification or controlled extension, and batch boundaries.
1. Design and review specification frontmatter, catalog summary, obligations, conditions, cardinalities, states, finished-document frontmatter rules, projections, presentation, supporting content, source binding, and coverage. Evaluate ordinary, incomplete, and boundary finished instances under EVAL-01 and EVAL-02; retain actual procedures, results, and failed attempts. Freeze literal text and change to `ready` only after required gates pass.
1. Compose under CMP-01 and CMP-02. Derive identities and paths under SEL-04. Additions never overwrite; authorized revisions check and retain their previous-byte binding.
1. Integrate [INDEX.csv](INDEX.csv), entrypoint counts, and [CHANGELOG.md](CHANGELOG.md) under CAT-01 through CAT-04.
1. Apply every acceptance gate below. Compare against the ready request, not a template with placeholders. Recheck sources if the working tree changed during authoring.
1. Report created IDs and files, compatibility scope, checks actually run, unresolved facts, and that publication or adoption has occurred only when supported by an actual decision.

| Gate | Pass evidence | Failure treatment |
| --- | --- | --- |
| Input | Exact key and type checks; sorted JSON keys; ready; current library HEAD and working sources; registry version and digest; no template markers; valid identities, conditions, references, cardinalities, and revision bindings. | Stop composition; name the defect. |
| Frontmatter and Rule 13 | Specification YAML frontmatter validates against the 5-key Semantic-Discovery schema (`title`, `description` 60–140 words, `topics` 3–12, `use_when` 2–6, conditional `not_for` 1–5) with zero Rule 13 leaks and zero unresolved delimiters; finished-document contract requires compliant 5-key frontmatter on standalone GFM outputs. | Fix frontmatter metadata or contract wording and revalidate. |
| Mission coverage | Independent source and task inventory; applicable information maps to obligations, content, and observable cases; exclusions justified; unknowns and stopping rules visible. | Expose omitted information or missing source before composition. Internal references alone do not pass. |
| Selection | Inspected comparisons establish reuse or a distinct purpose or applicability; family and variant rules are resolved; batch files do not duplicate responsibilities. | Use the existing type or return the unresolved selection decision. |
| Representation | Registered family or established extension; consistent 5-key frontmatter, title, syntax, metadata, snapshot, and authority rules for every supported projection; proportionate semantic roles and justified support. | Resolve conflict; do not force native data into an incompatible view. |
| Finished-instance use | Checked ordinary, incomplete, and relevant boundary cases including valid 5-key frontmatter; reader retrieves and uses necessary information; actual method, source, contract, and fixture bindings, outcomes, failures, and limits retained. | Keep required unresolved checks open; no invented success or substitution of static inspection for execution. |
| Composition | Literal CMP-02 agreement; leading 5-key YAML frontmatter; five H2s; correct bullets, compact GFM tables (`\| --- \|`), and controlled support; scope and client rules; exact UTF-8 LF bytes. | Correct request or output and repeat. |
| Semantics | Roles, definitions, input requirements, condition predicates, states, forms, and quality coverage agree; claims and authority rules preserve TXT-02. | Identify contradictory or unsupported content. A syntax pass cannot clear this gate. |
| Integration | Every live `*.spec.md` has exactly one matching [INDEX.csv](INDEX.csv) row; valid RFC 4180 CRLF CSV; paths resolve; deterministic ordering; actual counts and changelog match the contribution. | Correct catalog integration before reporting readiness. |
| Compatibility | Existing specifications are unchanged unless explicitly included in scope; no missing-file links or fabricated authority appear in changed entrypoints. | Explain and correct unintended changes. |
| Delivery | Actual checks and limits are stated; draft, review-ready, adopted, and published states remain distinct. | Keep the result visibly pending rather than inventing approval. |

A human or an agent can apply structural gates by inspection or a declared checker. No installed automated validator or renderer is supplied by the library. A syntax or composition check cannot establish source completeness, semantic truth, reader effectiveness, or actual execution. State each check's real scope. Live behavioral compliance across models and harnesses is not established.
