# Host document authoring profile specification

## Identity and selection

- **Specification ID:** `DOCUMENT-AUTHORING-PROFILE@host`.
- **Specification edition:** `1.0`.
- **Purpose:** Maintain a host's declared document-authoring values, actor assignments, authority boundaries, conventions, and provenance.
- **Intended readers:** Host document authors, accountable maintainers, reviewers, and the authorities responsible for the declared assignments.
- **Decision or action supported:** Determine which declared values and responsible actors apply to authoring for one host and which decisions remain specific to each document.
- **Use when:** One host needs a reusable, revision-controlled source of document-personalization values agreed for that host.
- **Scope boundaries:** Control authoring values for one identified host; exclude document-type contracts, publication procedures, access grants, per-document approvals, and incident histories.

## Authoring inputs and unresolved facts

Obtain the host identifier and applicability, organizational context or assessed absence, profile identity and edition, actual maintainer, declared actors with names, positions and nonsecret internal IDs, applicable role assignments and decision rights, agreed authoring and handling conventions, source locators and relevant revisions, actual verification information, and the profile's own decision state and dates. Obtain established process or service responsibility references only when they affect these assignments. Distinguish future target-document facts from reusable conventions and identify a predecessor and transition only when they actually exist.

For an unknown, undecided, conflicting, or inapplicable value, state the missing fact or assessed exclusion, its consequence, the resolving action, and the actual owner if assigned. Keep unresolved identity, mandate, scope, profile approval or effectivity visibly proposed or blocked for the affected use; no file location, current date, generic role, account, or source digest supplies the missing decision. An effective profile requires resolved applicable declarations and actual decision support; never invent a person, ID, approval, event, source edition, or observed result.

## Finished-document contract

- **Title:** Identify the one host and name the document as its document authoring profile.
- **Frontmatter:** None. Begin with the standalone GFM title; put profile identity, state, and value declarations in the body. Governing source: Type-owned DOCUMENT-AUTHORING-PROFILE@host policy; no external publication metadata schema is selected.
- **Client or receiving party:** Conditional body element in the identity or scope section. Include it only when a named external party commissions or receives the work; then state that party's established name and relationship, such as client or receiving organization. When no external party exists, state that the document has no external client. Do not invent a party. Do not put the party in the specification ID, filename, or type name.
- **Order:** State profile identity, host scope, and state before the initial declarations; resolve actor and authority references before their dependent interpretation; place source, limitation, and change information with or after the values it qualifies.
- **Presentation:** Use a compact declaration table and repeated record tables near the start, with concise prose for limits and history. Required semantic roles may share sections when every field, condition, source, and unresolved fact remains retrievable; do not require a separate chapter per role.

| Projection | Title and metadata ownership | Syntax and source authority |
|---|---|---|
| Host authoring profile (standalone) | The profile owns one H1 identifying its host and purpose. Profile ID, own edition, host scope, state, and declarations are body content, not inherited host-application metadata. | Use GFM tables and prose for the declared values and repeated actor, assignment, and source records; no native executable schema or parser is selected. The identified profile edition controls only its declared authoring values within scope. Bind their actual sources and revisions, resolve material conflicts, and reassess changed facts before claiming current applicability; neither this view nor a source locator grants approval. |

Missing, conflicting, out-of-scope, withdrawn, or superseded values prevent the affected current-use claim; state the gap, consequence, resolving action, and assigned owner when known. |

## Content definitions and forms

| Element | Meaning and cardinality | Constraint |
|---|---|---|
| Host and profile identity | Exactly one host ID, profile ID, profile edition, applicability boundary, and profile state in Profile identity, host scope, and state. | Use stable nonsecret identifiers and a version that distinguishes changed values. Do not equate a host alias with a network address or infer applicability from file location. |
| Declared value | One value or explicit gap for every applicable Declaration vocabulary field in Initial value declarations. | A declared value is authoring data with identified scope and basis. Unknown, not yet decided, and not applicable differ; explain consequential gaps and never treat an empty field as a default. |
| Actor | One record per distinct actor in Actors, assignments, and authority; one or more actors are needed for an effective profile. | An internal ID identifies the same actor over time. Name and position identify an issuing person; an ID is not a secret or a government identity document. Contact and affiliation are conditional on actual need and disclosure permission. |
| Role assignment | One or more applicable assignments in Actors, assignments, and authority; zero assignments for an explicitly unused role. | Each role reference identifies an existing actor and an explicit scope; resolve conflicting overlapping assignments before use. Repeated actor references across roles are valid, but cannot establish independent review. |
| Mandate | One actual basis and applicable limits per issuer, approver, or exception-authority assignment in Actors, assignments, and authority. | A proposed authority remains proposed until its actual assignment is established. Naming a role or recording a document does not grant the represented authority. |
| Source binding | One or more source entries covering all material declared values and state claims in Value sources, interpretation, and limits. | Identify actual sources with relevant edition or revision, verification time and verifying actor. A source may cover several named variables; a digest identifies content, not approval. Preserve source precision and time-zone or offset information for timed facts. |
| Convention | One declared rule or explicit disposition per applicable convention in Initial value declarations. | Conventions may govern language, time and date representation, document IDs, local editions, review, classification, distribution, retention, and exceptions. Do not infer a legal retention duty, source-specification edition, or target-document decision from a formatting convention. |
| Profile state | Exactly one of proposed, approved-awaiting-effect, effective, superseded, or withdrawn per profile edition in Profile identity, host scope, and state. | Only actual decisions support approval, effectivity, replacement, or withdrawal. A proposal may become approved-awaiting-effect or effective when the corresponding decision exists; an approved-awaiting-effect edition becomes effective only under its decided conditions. A proposed, approved-awaiting-effect, or effective edition may be withdrawn by decision; an effective edition becomes superseded only by an identified replacement and transition. A changed or reintroduced edition starts with its own proposed state rather than reactivating historical approval. |
| Responsibility reference | One per established process or system or service assignment covered by Process or service responsibility references; zero when that conditional role is inapplicable. | Bind the established context identifier, actor, applicability, and source. Missing event evidence cannot be supplied by the document author's identity or a reusable role assignment. |
| Historical binding and change | Exactly one maintenance rule and zero or one predecessor edition per profile edition in Maintenance and historical applicability. | A historical use identifies the profile ID and exact edition. Changed assignments affect only their decided applicability; retain earlier attribution and distinguish the profile's own approval and effectivity from those of every target document. |

Use the Declaration vocabulary as the field contract for the finished profile's initial variables and repeated records. Fill applicable declarations with established values; do not copy a blank form or specimen into an effective profile. The profile's actual edition and its sourced declarations control this authoring data; no new parser, skill workflow, installation path, publication procedure, or universal retention or review interval is prescribed.

### Declaration vocabulary

The following vocabulary defines authoring data, not executable configuration or a blank production record. Put resolved declarations near the start of the finished profile. Semicolon-separated names identify separate variables; prefixed record groups repeat by their stated identity. Each variable or record has one controlling value within its applicability. Do not add a reusable target-document approval, effective date, observed result, or event identifier.

| Variable or record fields | Inclusion and value rule | Interpretation and source constraint |
|---|---|---|
| PROFILE_ID; PROFILE_EDITION | Required: one nonempty identifier and one unambiguous local edition for this profile. | Identify this profile's controlled content, not a source specification's edition or another document's identity. |
| HOST_ID; APPLICABILITY | Required: one nonsecret host identifier and an explicit covered host, work context, document scope, and exclusions. | A file path, environment account, or current machine name alone is not an applicability decision. |
| EXTERNAL_CLIENT | Required to address for this profile's actual commissioning or receiving relationship. | Name an established external party and relationship, or state that this profile has no external client; do not make the profile's client a default for other documents. |
| ORGANIZATION; UNIT | Conditional on an established organizational relationship. | Use declared names; state assessed absence or inapplicability without inventing an organization. |
| PROFILE_STATE; MAINTAINER_ID | Required: the controlled profile state and one actor reference or an explicit assignment gap. | Use the defined Profile state vocabulary; an unresolved maintainer blocks effective applicability. |
| PROFILE_APPROVAL_REF; PROFILE_APPROVED_ON; PROFILE_EFFECTIVE_ON | Required to address for this profile; actual decision reference and dates are required for the claimed approved or effective state. | For a proposal, identify the unresolved decision instead of borrowing another edition's approval. Preserve distinct approval and effect dates and source precision. |
| PROFILE_REVIEW_RULE; SUPERSEDES; TRANSITION_RULE | Review rule required; predecessor and transition conditional on replacing an edition. | Name an actual predecessor and decided transition; do not infer retroactive effect or delete history. |
| ACTORS: ACTOR_ID; NAME; POSITION | One record per actor; each effective assignment resolves a nonempty ID, declared name, and position or established role. | The issuing person's name, position, and internal ID remain independently retrievable; one actor may fill several roles. |
| ACTORS: ORGANIZATION; CONTACT_REF | Conditional on actual affiliation or a needed established internal contact route. | Use only necessary authorized information, not credentials, private keys, government identity numbers, or inferred personal details. |
| ASSIGNMENTS: ROLE; ACTOR_ID; APPLICABILITY | One record per applicable author, issuer, maintainer, reviewer, approver, or exception-authority assignment. | Use the stated role labels, an existing actor ID, and decidable scope; document unused roles and unresolved overlaps. |
| ASSIGNMENTS: AUTHORITY_BASIS; LIMITS | Basis required for issuer, approver, and exception authority; limits required to address for those assignments. | State the actual mandate and its scope, conditions, and expiry when established; an unknown material limit blocks dependent authority claims. |
| LANGUAGE; TIME_ZONE; DATE_FORMAT; TIMESTAMP_FORMAT | One agreed value or disposition per applicable representation convention. | Use an established language and time zone; timed facts retain offsets or time-zone context and actual precision. Do not guess the host time zone from the author's session. |
| DOCUMENT_ID_RULE; LOCAL_EDITION_RULE; DOCUMENT_REVIEW_RULE | One agreed rule or explicit disposition per applicable document-control convention. | Define identity uniqueness, revision meaning, and review triggers without predeclaring a particular target document's ID, edition, next review date, or approval. |
| CLASSIFICATION; DISTRIBUTION; RETENTION_RULE; EXCEPTION_RULE | One agreed rule or explicit disposition per applicable handling convention. | State the actual protection, audience, retention basis, and permitted exception boundaries; do not infer disclosure permission or a legal duty. |
| SOURCES: SOURCE_ID; LOCATOR; REVISION; APPLIES_TO | One record per actual source or coherent source group, covering all material variables and decisions. | Use a source ID, usable locator, relevant edition or revision, and covered variable or record names; source absence remains an explicit gap. |
| SOURCES: VERIFIED_AT; VERIFIED_BY | One actual verification time and verifying actor reference per source entry, or an explicit verification gap. | Distinguish verification time from preparation, approval, effectivity, and any underlying event time; do not manufacture exact timestamps. |
| RESPONSIBILITY_LINKS: CONTEXT_REF; ACTOR_ID; APPLICABILITY; SOURCE_REF | Conditional: one record per in-scope process or system or service responsibility relied on by the profile. | Resolve the established context, responsible actor, boundary, and source; leave actual change and event attribution to their own evidence. |

## Quality criteria

- The profile identifies exactly one host, its applicability, profile ID and own edition, truthful state, maintainer, and organizational or client dispositions without implying permission from its location.
- Applicable variables occur near the beginning, use the declared vocabulary, and resolve to concrete sourced values or explicit gaps; no effective profile retains unfilled markers or consequential unknowns.
- Actor IDs are unique and role references resolve; each issuing person has retrievable name, position, internal ID and actual mandate with scope and limits. Multi-role assignments do not fabricate independent review.
- Material identity, authority, convention and state claims have identifiable sources, revisions, verification time and actor; gaps and conflicts expose their consequence and resolution route without fabricated facts.
- Profile approval and effectivity remain distinct from every target document's decisions, source-specification edition, observed results and event facts; a target document retains its selected type contract.
- Conditional process or service references identify their actual context, actor and source without becoming an inventory or asserting event execution or causal responsibility.
- Review, replacement and transition remain bound to actual profile editions and decisions; changed roles preserve historical attribution and do not reuse actor IDs or transfer earlier approval.
- Out-of-scope, unresolved, conflicting or inactive declarations prevent the affected current-use claim, and the profile contains no secrets or unnecessary personal or infrastructure data.
